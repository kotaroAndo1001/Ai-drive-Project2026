# リアルタイムチャット 要件定義書（`docs/chat/02_requirements.md`）

入力: `docs/chat/01_request.md`（WISH-CHAT-001〜005）、既存アプリの構成（下記 1.5）
記録日: 2026-11-25

---

## 1. 目的・利用者・範囲

### 1.1 目的

既存の Express / TypeScript アプリ（TOP・TODO・AI質問 V1/V2）に、利用者同士がリアルタイムに会話できる `/chat` を追加する。
ブラウザから送ったコメントが「どこで検証され（サーバー）」「どこに保存され（Neon `chat_messages`）」「誰に配信されるか（同じルームに入室済みの接続）」を説明できる構成にする。

### 1.2 利用者

- 一般ユーザー・管理者：どちらも同じ画面で、ユーザー名とコメントを入力して使う。
- 既存アプリにログイン機能はない。ユーザー名は**画面表示用の自己申告の入力値**として扱い、本人確認には使わない。

### 1.3 対象範囲

- `/chat` 画面（EJS）とブラウザ側スクリプト（`public/chat/chat.js`）
- Socket.IO による入室・投稿・同じルームへの配信
- Neon への投稿保存と、入室時・再入室時の最新20件表示
- 1ルーム5人の定員（全インスタンス合計）と満席時の制限
- 複数インスタンス間の新着同期（DB 同期方式）
- 入力検証・エラー表示・XSS 対策・秘密情報の管理

### 1.4 対象外

- AI による自動応答（チャットでは扱わない）
- 複数ルームの作成・切り替え（ルームは `lobby` の1つだけ）
- ログイン・本人確認、DM、既読、編集・削除、添付ファイル
- Vercel Functions 上でのリアルタイム通信の提供（1.6 参照）

### 1.5 既存機能との関係（実コードで確認した内容）

| 項目 | 確認結果 |
|---|---|
| 起動ファイル | `index.ts`（`local.ts` は存在しない）。`app.listen(3000)` で起動 |
| npm スクリプト | `dev`（`tsx watch ./index.ts`）、`build`（`tsc`）、`start`（`node ./dist/index.js`） |
| 既存ルート | `/`、`/api/db-check`、`/db-sample`、`/todo`、`/api/v1/todos`、`/ai`、`/api/ai/*`、`/ai/v2`、`/api/ai/v2/*` |
| DB 接続 | `db.ts` の `pool`（環境変数 `DATABASE_URL`）。`DATABASE_URL_POOLED` は未使用 |
| 404 / エラー | 独自 404 ハンドラーはなく Express 既定の 404。JSON 破損・サイズ超過用のエラーハンドラーが1つある |
| 認証 | なし |
| 構成パターン | `src/apps/todo/`（Router / Controller / Model）、AI は Service 層あり |
| SQL 番号 | 000, 010, 020（todo）, 030・040（ai）使用済み → チャットは **050** |

### 1.6 配置先

- 既存の公開先は Vercel。Vercel Functions は WebSocket サーバーを常駐できず、最大実行時間で接続が切れる。**リアルタイム通信の検証はローカル（1台・2プロセス）で行う。** Vercel 上の `/chat` は画面が表示され、接続できない場合は「接続できません」と案内できればよい（**要確認**：本番でチャットを公開するか、常駐サーバーを別に用意するか）。

|---|---|---|---|
| REQ-CHAT-001 | WISH-CHAT-001 | `GET /chat` で EJS のチャット画面を返す | HTTP 200。ユーザー名欄・コメント欄・送信ボタン・投稿一覧・状態表示がある。TOP から `/chat` へのリンクがある |

| REQ-CHAT-005 | WISH-CHAT-002 | 入室時と再入室時に、最新20件を古い順に表示する | 21件以上ある状態で入室すると、最新20件だけが古い→新しい順に表示される。履歴取得中に届いた新着も重複せず1件だけ表示される |
| REQ-CHAT-006 | WISH-CHAT-003 | 別インスタンスに接続した利用者にも新着が届く（DB 同期） | ポート3000と3001の2プロセスに分かれた接続同士で、双方向に新着が届く（ポーリング間隔ぶん遅れてよい） |
| REQ-CHAT-007 | WISH-CHAT-004 | 同時入室は全インスタンス合計で1ルーム5接続まで | 5接続が入室済みのとき6接続目は入室できない。2台から同時に入室要求しても合計5を超えない |

| REQ-CHAT-011 | 非機能 | 秘密情報をサーバーだけで扱い、XSS を防ぎ、既存機能を壊さない | 画面・JS に接続文字列が含まれない。`<script>` などはそのまま文字として表示される。TOP・TODO・AI・404 が従来どおり |

## 3. 画面・配信・履歴・定員の詳細

### 3.1 `/chat` の初期表示

1. 画面を表示し、Socket.IO で接続する（接続しただけでは入室ではない）。
2. 接続後に入室を要求する。許可されたら最新20件を表示し、送信フォームを有効にする。
3. 拒否（満席）なら満席案内を表示し、履歴とフォームは表示しない。

### 3.2 投稿から配信まで

1. ブラウザがユーザー名とコメントを送る。
2. サーバーが「入室済みか」「型」「前後空白を除いた長さ」を検証する。
3. Neon に保存し、DB が確定した ID・ユーザー名・コメント・作成日時を得る。
4. 同じルームの入室済み接続（送信者を含む）へ配信する。送信者には受理結果（ack）も返す。
5. 画面への追加は**配信を受け取ったときだけ**行い、投稿 ID で重複を除く（送信者の二重表示を防ぐ）。
6. 入力不正・保存失敗では配信せず、送信者にだけ理由を返す。ack が時間内に返らない場合は「保存できたか不明のため一覧を確認してください」と表示し、自動再送はしない。

### 3.3 履歴（最新20件）

- 最新20件を選び、その20件を古い順（作成日時、同時刻は ID 順）に並べる。新着は一覧の下に追加する。
- 履歴取得中に届いた新着と履歴を投稿 ID で統合し、1件ずつにする。
- 履歴の取得に失敗したら「履歴を取得できませんでした」と再試行ボタンを表示する。
- 20件より前の履歴の閲覧は対象外。

### 3.4 定員（1ルーム5人）

- **数え方：入室済みの Socket 接続単位で5つまで**（確定）。同じ人が2タブで入室すると2席使う（テストで記録する）。
- 5接続入室済みのとき、6つ目は「満席です。しばらくしてから再試行してください」と再試行ボタンを表示する。
- 満席の接続はルームに参加させないため、履歴・新着は届かない。投稿もサーバーで拒否する。
- 切断・タブを閉じる・入室処理の失敗で席を解放する。プロセスの異常終了で残った席は、一定時間（30秒）更新がなければ回収する。
- 再接続したら自動で再入室し、許可後に最新20件を取り直す。再入室時に満席なら満席案内を表示する。

## 4. 入力・エラー・セキュリティ・回帰

### 4.1 入力検証

| 項目 | 条件 |
|---|---|
| 型 | `username`・`comment` とも文字列。数値・配列・オブジェクト・未指定は拒否 |
| 前後空白 | 前後の空白（全角スペース・改行・タブを含む）を除いてから判定・保存する |
| 長さ | 前後空白を除いた後の文字数（サロゲートペアは1文字）で、ユーザー名1〜50、コメント1〜500 |
| 改行 | コメント中の改行は許可し、そのまま表示する |
| 二重検証 | ブラウザでも事前に確認するが、判定の正はサーバー |

### 4.2 エラー時の表示

| 状況 | 画面の表示 | サーバー |
|---|---|---|
| 未接続・切断中 | 「接続が切れています。再接続中…」、送信ボタン無効 | 切断時に席を解放 |
| 入室前・満席で送信 | 「入室していないため送信できません」 | 保存・配信しない |
| 入力不正 | 項目ごとの理由 | 保存・配信しない |
| DB 障害（入室・履歴・投稿） | 「サーバーで保存できませんでした。時間をおいて再試行してください」 | ログを出して処理を継続 |
| ack タイムアウト | 「保存できたか確認できません。一覧を確認してから再送してください」 | — |

### 4.3 秘密情報・XSS

- `DATABASE_URL` はサーバーの `db.ts` だけで読む。新しい環境変数は `PORT`（任意、既定 3000）のみ。Redis は使わない。
- 投稿の表示は `textContent` のみ。EJS では利用者入力を出力しない（出力する場合も `<%= %>`）。

### 4.4 回帰確認

TOP、`/api/db-check`、TODO（画面・API）、AI 質問 V1/V2 画面、存在しない URL の 404、JSON 破損時の 400。

## 5. 複数インスタンス

| 項目 | 要件 |
|---|---|
| 新着の同期 | 各インスタンスが DB を定期取得（2秒間隔）し、自分の入室者へ未配信の新着を配信する。ブラウザは投稿 ID で重複を除く |
| 定員 | 席は DB の共有テーブルで管理し、ルーム行をロックしたトランザクションで「数える＋確保」を一度に行う。全台合計で5 |
| 異常終了 | 各インスタンスが10秒ごとに自分の席の最終確認時刻を更新し、30秒更新のない席は次の入室判定で回収する |
| 共有状態を確認できない | DB に接続できない場合は入室を許可しない（定員超過より安全側） |
| ローカルで確認 | `PORT=3000` と `PORT=3001` の2プロセスを同じ DB で起動して確認する |
| 複数台で確認 | 本番の複数台構成は環境がないため未実施とし、必要な環境を記録する |
